# Shared implementation contract

This is Axiom 2.0.0, a runnable, loopback-only reference application with local fixtures, an optional model provider, and a governed outbound-integration gateway. It uses database schema 11, built-in deterministic-agent contract 1.3.0, a Python standard-library server, SQLite, and a vanilla JavaScript/CSS interface. Schema 10 added durable adaptive Goal Agent specifications, published versions, sessions, and workflow-child bindings; schema 11 adds versioned external connections and generation-bound health records. It is not a deployed multi-tenant service, a distributed worker system, proof of live-model quality, or proof of any live Slack/Jira/Confluence/CSR/OCI/email/finance/directory integration.

## Session and API boundary

API errors use `{error:{code,message,details?}}`. `GET /api/bootstrap` creates a local development session when needed and returns the current user, seeded users, CSRF token, agents, templates, runs, approvals, redacted public connection records, and capability/limitation labels. `POST /api/session {userId}` switches among the seeded author/admin, reviewer, operator, and contributor accounts. All mutations require the session CSRF token and same-origin localhost host/origin checks. Request JSON must be one object encoded as strict RFC 8259 data; duplicate object keys, `NaN`/infinities, and unpaired Unicode surrogates are rejected. These identities are development fixtures, not OIDC.

`GET /api/health` reports the local SQLite runtime, Axiom version, and highest applied schema migration. Migrations are ordered and idempotent. Before schema changes, startup verifies existing JSON records with the same strict decoder and refuses an ambiguous or non-interoperable legacy record without changing the schema. Persisted JSON is emitted canonically with finite numbers and valid Unicode. The server binds to `127.0.0.1` only.

## Domain and workflow contract

`domain.py` owns canonical JSON/hash behavior, a constrained JSON-Schema subset, instance validation, conservative assignability checks, a bounded typed rule AST, and separate semantic/layout hashes. Unsupported schema/rule constructs fail closed. Within the supported subset, assignability covers types, scalar and array bounds, finite enums/constants, nested required/optional properties, item schemas, and closed or typed additional properties. It is not general JSON Schema.

`workflow.py` validates and compiles a bounded DAG with Agent, Condition plus explicit merge, Parallel split plus paired Join, Approval, Outcome, End, and bounded Delay types. It rejects cycles, duplicate/dangling edges, invalid roots/sinks, unsupported types, missing condition defaults, branch crossings, mismatched scopes, and graph limits. Legacy agent-only DAGs remain supported. Publication stores the schema/compiler/interpreter/policy versions, one pinned agent version and complete manifest per graph node, the compiled plan, semantic/layout hashes, and any bounded demonstration fixture manifest and defaults in the immutable snapshot. Demonstration fixture data is canonicalized, hashed, and checked against the published graph before execution.

The local scheduler remains the single execution authority. It executes dependency branches, typed conditions, skipped branches, joins, outcomes, approvals, and manual handoffs using persisted SQLite run state. It is not a distributed engine and has no production failover or scale claim.

## Agents and SDK

Agent records contain stable ID, implementation alias, version, constrained input/output/config schemas, side-effect class, retry safety, capabilities, lifecycle, and fixture metadata. Built-ins include intake, CSR fixture, policy, ownership, approval, local ticket, receipt, enrichment, condition, parallel, join, outcome, and end. Built-in output contracts declare the fields their adapters produce, so mappings can be checked before publication.

`GET/POST /api/agents`, `PUT /api/agents/:id`, `DELETE /api/agents/:id`, and `POST /api/agents/:id/deprecate` implement the local registry lifecycle. Deletion is administrator-only, refuses built-ins and anything referenced by a draft, release, or run, and is therefore limited to unused custom registrations. Deprecation blocks new draft placement/releases while preserving immutable published execution. `GET /api/agents/:id/impact?targetVersion=...&fromVersion=...` returns deterministic impact analysis over supplied local releases.

The administrator interface reaches agent registration from the Agent Registry, the Studio step palette, and the empty-canvas action menu. Metadata editing is available from the Registry contract view and a placed node's **Edit reusable agent details** action. Registration selects an existing local implementation alias; these paths do not accept arbitrary executable packages. Changing shared metadata keeps the stable agent ID, while already published snapshots retain their pinned contract.

`agent_sdk.py` provides a validated versioned manifest, input/config/output checks, a connector boundary limited to approved named operations, redacted structured logging, and a non-overwriting local scaffolder. It is a tested domain/developer contract; generated packages are not dynamically installed or registered by the server.

## Adaptive Agent Factory and Goal Agent sessions

`agent_factory.py` is one shared registry-driven runtime rather than a collection of domain-specific agent implementations. A capability contract has a stable ID and version, business description, strict input/output schemas, effect classification, authorization contract, adapter binding, idempotency/reconciliation metadata, examples, and verification state. Executable adapters remain developer-registered trusted code; an agent specification cannot upload code, invent a tool, expand its own authority, or turn an arbitrary URL or model-produced program into an executable capability.

An agent specification has stable identity and version, mission, operating instructions, permitted context paths, allowed capability IDs, strict input/result schemas, required evidence tools, stop/escalation rules, policy references, evaluation cases, and bounded turn, tool, write, context, output, time, model-token, and estimated-cost limits. `POST /api/agent-specs` creates an administrator-authored draft. `PUT /api/agent-specs/:id {expectedRevision,...}` updates the candidate with optimistic concurrency. A draft is not palette authority. `POST /api/agent-specs/:id/publish {expectedRevision}` requires a different reviewer and publishes the exact version; only then does the server register its immutable Goal Agent alias for new workflow placements. Older workflows and sessions retain their pinned versions.

`GET /api/agent-factory` returns the role-filtered specification catalog, capability contracts, readable sessions, controlled fixture scenarios, and configured-provider state. `POST /api/agent-specs/propose {brief}` calls the configured model outside the persistence lock and returns a compiled, reviewable proposal with `saved:false`, `requiresReview:true`, and no self-authorized permissions. An absent provider returns a visible configuration error; no scripted proposal is substituted.

`POST /api/agent-runs` starts a published version in explicit `model` or eligible `fixture` mode. `GET /api/agent-runs` and `GET /api/agent-runs/:id` return authorized durable records. `/advance`, `/clarify`, `/decision`, and `/stop` are role-checked mutations. Each model turn receives the mission, projected permitted input, selected attributable observations, outstanding questions, authorized tool contracts, constraints, and remaining budget. It must return one strict structured decision: call an allowed capability, request declared missing fields, or finish with a typed output and evidence references. Unknown fields, tools, references, arguments, or alternatives fail closed.

Model/provider I/O occurs outside the SQLite/runtime lock. A completion is applied only when its worker lease, claimed revision, and session still match; late or stale responses are ignored. The model never grants permissions, changes its mission, removes approval, or claims an effect succeeded without a validated adapter result. Durable history is stored separately from the selected model context. Failed reads can become bounded observations for another decision; uncertain writes stop for reconciliation rather than being retried blindly.

Context selection and authorization are separate. Initial input is projected only through declared paths, and observations retain tool ID, resolved arguments, status, action hash, and result hash. The runtime does not send the entire database, arbitrary workflow history, secrets, or undeclared inputs to the provider. Capability discovery is restricted to the already authorized specification allowlist.

Every adaptive write pauses as an exact prepared action. The durable action binds the capability and tool version, authoritative adapter target, stable operation key, exact arguments and payload hash, approval requirement, authorization scope and policy references, evidence references and source-result versions, reconciliation contract, and action fingerprint. The host effect ledger stores the same protected preparation. Review submits the displayed fingerprint; payload, target, policy, evidence, version, or business-precondition changes invalidate the decision. The stored action—not a model reconstruction—is dispatched after approval. Local fixtures implement their tested idempotency/reconciliation contract; external adapters stop uncertain outcomes until destination-specific reconciliation is implemented or performed by an operator.

Kernel completion checks output-schema shape, cited evidence references, and required evidence-tool observations. These checks do not prove the requested business outcome. Bundled fixture domains separately run trusted source/receipt comparisons and return `outcomeValidation.status` as `satisfied`, `contradicted`, or `unknown`. Custom domains remain `unknown` until a developer registers an authoritative validator.

The bundled service, invoice, and access cases use a clearly labeled `scripted-fixture` decision provider. They run through the same validation, persistence, clarification, approval, effect, and result paths, but do not call an LLM or establish model quality. Configured model mode requires server-side `AXIOM_MODEL_ENDPOINT` and `AXIOM_MODEL_NAME`; API key and input/output price rates are optional server-side settings. The adapter permits HTTPS or loopback HTTP, rejects redirects and oversized or malformed responses, and never silently falls back to a fixture.

A published workflow Goal Agent node pins the approved specification version and contracts, creates or resumes one durable child session, and waits while the child plans, requests information, awaits exact-action approval, or stops. Node-level permission to start work is not approval for a consequential child action discovered later. Verified child completion supplies a typed result downstream; failure, cancellation, missing input, approval wait, and budget/deadline exhaustion remain explicit parent states.

## External connection gateway

`integrations.py` defines strict connection and capability contracts, reviewed provider presets, exact prepared calls, redacted public records, credential injection at dispatch, egress validation, bounded rate admission, response projection, retry classification, OpenAPI inspection primitives, and MCP client interfaces. The module does not discover authority for a model or make a descriptor executable by itself.

`GET /api/integration-catalog` returns provider descriptions and setup availability. `GET /api/connections` includes both fixture and external public records. `POST /api/connections` is administrator-only and accepts the reviewed Slack, Jira Cloud, Confluence Cloud, and outbound-webhook presets. It rejects browser-defined operations and currently rejects generic REST/OpenAPI and MCP creation with a developer-review-required state. `POST /api/integrations/openapi/inspect` accepts exactly one administrator-supplied, fully inlined OpenAPI 3.1 JSON document and returns a canonical hash plus non-executable review candidates; the audit record contains only hash/summary metadata. Authentication values must be `env:` references; inline credentials are rejected. Persisted records retain the reference so the server can resolve it, while public state returns only credential-slot/configuration/availability booleans and never the reference name or resolved value.

Native Slack and Atlassian connections accept only their exact official API origins and product paths. All outbound calls are built from one pinned base URL plus a reviewed operation template. The gateway rejects model-supplied destinations and headers, path traversal, unsafe schemes/ports, embedded URL credentials, disallowed private or metadata addresses, DNS rebinding results, redirects, oversized responses, and unsupported provider response shapes. Private-network destinations require both a connection opt-in and server setting `AXIOM_ALLOW_PRIVATE_CONNECTORS=1`.

`POST /api/connections/:id/test` executes only the provider preset's registered read-only health operation. A provider without such an operation exposes no test action. `POST /api/connections/:id/invoke` executes only an explicitly registered read operation; direct writes are refused. Network work occurs outside the persistence lock. Before applying a result, the server rechecks the connection version/generation/status so a stale response cannot restore health or become an observation. Call audit entries retain bounded operation metadata and hashes, not credentials or raw response bodies. `POST /api/connections/:id/revoke` and `/restore` are administrator-only generation-changing authority operations.

A ready external connection contributes stable per-connection capability IDs to Agent Factory. The capability is still usable only when selected by an approved specification and allowed for the caller. An adaptive external write persists the exact prepared target, method, headers without credentials, query, body, connection/version/generation, operation/version, stable operation key, limits, and plan hash. It always requires exact-action approval. The runtime verifies the stored plan, rechecks the current connection and relevant successful source reads, then dispatches the stored call; model output cannot recreate or redirect it after approval. Changed authority, source state, arguments, target, or contract invalidates the action.

The local host has no automatic external retry loop and no destination-specific external reconciliation implementation. Validated retry metadata and retry advice do not themselves dispatch another request. A write whose remote outcome may be unknown is recorded as unknown and stopped for provider-specific or human reconciliation; it is never reported as a normal failure or retried blindly. The application also lacks OAuth consent/callback/refresh, generic OpenAPI activation through HTTP/UI, a configured MCP host client, signed inbound webhooks, production secret storage, production identity, and tenant isolation. No live provider credentials were exercised by the recorded release verification.

## Templates, finding, planning, and publication

Template records contain stable identity, draft revision, lifecycle, published version, typed input schema, nodes/edges, and immutable versions. `POST /api/templates` creates an empty draft. `PUT /api/templates/:id` requires `expectedRevision`; stale writes fail. Validation rejects undeclared mapping targets/sources, incompatible types, non-upstream references, and values unavailable on every path. Submission freezes a candidate hash; reviewer publication refuses self-approval or a changed snapshot. `GET /api/templates/:id/diff` reports exact stored differences. Published records remain byte-for-byte historical records. When an older release needs newer safe execution metadata, schema migration creates a separately hashed `axiom.release-compatibility.v1` snapshot bound to the original version and release hash, preserves the prior compatibility record in history, and audits the replacement. Execution verifies both hashes and their binding before using the overlay; it never treats the overlay as a new publication.

After the browser creates an empty template, it selects that draft and opens the reusable-agent palette immediately. Step placement, movement, configuration, connected insertion, duplication, mapping, and removal remain unsaved browser draft changes until revision-aware `PUT /api/templates/:id` succeeds. Connected insertion creates one explicit edge; duplication deep-copies the node configuration but does not silently copy its connections. Node, edge, and empty-canvas context menus expose these operations according to the current role and template lifecycle, and destructive removal still requires confirmation.

Administrator-only duplicate/archive/restore and import actions are exposed under `/api/templates`; export is read-only. Duplication creates an independent unpublished draft. Archiving blocks new fixture starts, draft simulations, and rehearsal experiments while preserving releases, history, and existing runs. Restore retains release history and re-enables eligible new work. `axiom.template-export.v1` packages contain a canonical SHA-256 hash and imports recheck that hash plus current graph/schema/approval rules. The hash is an integrity check, not a signer identity or digital signature.

`GET /api/templates/find?q=...` searches only active published templates startable by the current local principal. Scores are deterministic keyword matches with an explanation and only supplied template IDs. It is not a generative recommender.

`POST /api/plan` produces a reviewed local or configured-model proposal and never edits automatically. `POST /api/plan/:id/apply {expectedRevision}` rechecks the base revision and normal validation. At most 100 operations are accepted from the allowlist: `update_node`, `add_node`, `remove_node`, `add_edge`, `remove_edge`, `bind_field`, `insert_approval`, and `replace_agent`. Removal cannot delete an approval boundary; replacement is limited to an active registration with the same implementation and effect class. Every candidate passes the same graph, schema, mapping, and approval validation as manual edits. This remains a bounded operation compiler, not the complete natural-language requirement compiler from the production prompt.

## Runs, decisions, effects, and recovery

`POST /api/runs` starts either isolated simulation from a draft or fixture execution from an immutable published snapshot. Run and node state, attempts, inputs/outputs, evidence, decisions, operation identities, events, attachment metadata, and the pinned graph survive restart. Fixture mode permits the happy and accepted-write/lost-acknowledgement cases; declared failures run in simulation so they cannot create ticket rows. An optional actor-scoped `idempotencyKey` binds the complete start request; the same key and request return the original run, while reuse with changed input or attachments fails.

`artifacts` on task start accepts at most five base64-encoded UTF-8 `application/json`, `text/plain`, or `text/csv` records, limited to 256 KiB each and 512 KiB total. Names, encoding, JSON syntax, duplicate names, per-file size, and total size fail atomically. The local database retains content for the run, while public run/evidence/artifact responses expose only metadata and SHA-256. This type validation is not malware scanning, content safety analysis, tenant storage, retention, or production object storage.

Manual Execute and Approve/Reject are separate server-authorized commands. Repeated decisions are idempotent; conflicting decisions fail. Cancellation stops new local work but does not erase completed effects. Reminders derive current local recipients from the required role, are rate-limited and deduplicated, and record queued/sent transitions, provider, connection generation, delivery key, and `/#review` deep link. `sent` means delivered to the persisted local capture outbox only; no external email or notification is sent, and a GET link never decides an approval.

Every write creates a persisted effect with `prepared`, `dispatched`, `acknowledged`, `unknown`, or `reconciled` state. The action fingerprint binds run/node/operation generation, canonical payload, and local connection identity including its authority generation. The approval-envelope hash also binds the local approval policy and evidence snapshot. Operation-key reuse with changed action data fails; an unknown accepted write must reconcile an exact operation-key, action-fingerprint, and protected-payload match before retry. `GET /api/runs/:id/effects` is read-only and returns aggregate state counts plus reduced effect summaries. It does not return the internal effect records or protected payloads.

Exact payload/envelope approval applies when the write node itself has `approvalRequired` and when an explicit Approval control directly guards one or more downstream protected writes on every path. The runtime prepares every downstream action before review; the decision must name the complete packet of effect, node, operation generation, action fingerprint, and approval-envelope hash references. Expired, incomplete, or changed preparations cannot dispatch. Current connection authority is checked before decision and again before dispatch. Administrator-only `test`, `revoke`, and `restore` actions on `/api/connections/:id/...` are audited; authority changes increment the connection generation. This contract applies to local fixture authorities and schema-11 external connections. Revocation blocks new writes without hiding a prior recorded outcome; only local fixture reconciliation is automated in this build.

`GET /api/runs/:id/repair` returns bounded deterministic diagnostics. `POST /api/runs/:id/retry` is explicit and allowed only for locally classified safe/reconciled failures. This does not claim universal exactly-once effects or compensation.

## Evidence and scenarios

`evidence.py` defines SourceSnapshot, Transformation, EvidenceItem, Claim, DecisionPacket, ActionReceipt, and EvidenceGraph. It validates source hashes, excerpt bounds, references, deterministic claim values, visible conflicts, access inheritance, receipt states, filtering, and secret-key redaction. `GET /api/runs/:id/evidence` builds an access-filtered graph from recorded local run evidence and effects. Authorized `POST /api/runs/:id/export` creates and audits an `axiom.run-export.v1` download containing the authorized run, evidence, reduced effect summary, pinned snapshot, generated Markdown summary, recursive sensitive-field redaction, hashed replacement for raw `externalContent`, and a canonical SHA-256 `manifestHash`. Export is deliberately not a side-effect-free GET because the export action is recorded. The hash is integrity-checkable but is not an HMAC, public-key signature, or proof of exporter identity. The graph is not yet a separate persistent provenance store backed by external source retention.

`GET /api/scenarios` exposes the versioned ten-case catalog: happy path, missing input, dependency timeout, approval rejection, approval expiry, revoked role, duplicate callback, conflicting evidence, lost acknowledgement, and malicious content. `POST /api/experiments {templateId,suite:'core'|'required'}` starts isolated draft simulations only for an active template. The experiment pins each scenario definition and fingerprint to its run, uses an experiment-scoped ephemeral destination instead of fixture write connections, and rejects a mismatched or changed pin set. `GET /api/experiments/:id` evaluates the pinned expected state, required event path, attempted-effect count, graph-derived authorization, duplicate operation keys, and absence of fixture tickets/outbox writes. A completed evaluation is itself fingerprinted and returned unchanged. Simulated human decisions are labeled.

`scenarios.py` additionally provides deterministic observation evaluation, paired release comparison, and regression-case creation. Those latter functions are domain services, not persisted HTTP workflows.

## P2 governance services and limits

`governance.py` contains validated domain services for versioned block expansion with fresh deterministic IDs/provenance, permission-filtered template search, agent-version impact analysis, bounded TeamRecipe planning with one commit actor and matched-budget baseline, and paired release selection that preserves active-run pins and blocks unsafe candidates.

Only template finding and agent impact currently have server routes. Blocks, TeamRecipe execution planning, paired release selection, and environment promotion have no persistence or user interface and must not be described as completed workflows.

## Seed, audit, and static interface

The database seeds six published workflows. The legacy CSR graph is intake → CSR, then policy and ownership branches → approval → local ticket → receipt. Five additional demonstrations cover payment dispute investigation, employee access governance, production incident and change control, vendor risk and procurement onboarding, and insurance claim adjudication. Each demonstration has 14 nodes and 16 edges with typed required domain input, parallel checks, a condition whose two routes are tested, exact full-action approval, one simulated local record, and a receipt. Missing built-in seed IDs are backfilled at startup without replacing an existing workflow stored under the same ID.

The demonstration releases pin and hash their bounded fixture manifest and defaults. The fixture profiles produce deterministic domain-specific records and evidence for repeatable demos; they are not external payment, identity, monitoring, procurement, insurance, Jira, OCI, or email integrations. Their required-case suites assert no external or unauthorized writes; current release results belong in the QA record rather than this contract. `GET /api/audit` returns recent local audit records. Static serving is restricted to the owned interface entry, JavaScript, CSS, and icons. JSON selected for task input is parsed in the browser; separate bounded JSON/text/CSV attachments are validated and stored locally by the server. Neither path is a production upload, malware-scanning, retention, or object-storage service.

The interface provides Agent Factory, Studio, Capability Registry, Runs, Review Inbox, Rehearsal, Connections, and Audit views over the local API. Agent Factory exposes the draft/activation lifecycle, business-oriented specification editor with advanced schemas and limits, provider labels, actual action/observation history, scoped clarification, exact-action records, completion/outcome checks, and fixture-only behavior comparison. Connections shows the provider catalog, reviewed operations, derived scopes, environment-reference fields, credential availability, health, authority generation, and allowed lifecycle actions; generic REST/OpenAPI and MCP show their developer-review-required state instead of a dead Connect action. The task-start dialog includes permission-filtered published-template search. Workflow approval displays the exact prepared action; run views expose redacted effect and evidence ledgers. Draft nodes provide a visible action button as well as right-click access; the Context Menu key or **Shift+F10** opens node, edge, and focused-canvas menus, and Arrow/Home/End/Escape provide menu navigation and dismissal. **Ctrl/Cmd+S**, **Ctrl/Cmd+D**, and **Ctrl/Cmd+Z** cover save, selected-node duplication, and undo. Mutation controls remain disabled for read-only roles and frozen or archived templates.

The day/night control stores only `light` or `dark` under the browser-local `axiom.theme` key, applies the preference before first paint, and updates the browser theme color. It has no workflow API or database record. The read-only Studio banner can call the existing development-session endpoint to switch to the seeded administrator account, with confirmation before unsaved changes are discarded and the saved draft is reloaded. This is demonstration convenience over fixture identities, not OIDC, authorization delegation, or a production user-preference service.

The offline preview embeds captured records and refuses mutations. JavaScript/view-contract checks are supplemented by the recorded headed-browser journeys in `research/QA_NOTES.md`. The workflow-builder journey created and saved **Workflow Builder Quickstart**, retained a two-node/one-edge draft, exercised right-click rename/duplicate/confirmed removal, reviewer quick-switch, persisted night mode after reload, and responsive Save visibility. That evidence is not a full WCAG, cross-browser, collaborative-editing, production-identity, or production-security certification.

Real OIDC/directory mapping, multi-workspace tenant isolation, managed secret storage, full OAuth lifecycle, live tenant validation for the included external presets, generic OpenAPI activation, a configured MCP host client, inbound webhook verification, automatic external retries, provider-specific external reconciliation, OCI principal/key handling, live-model quality and adversarial evaluations, provider privacy/retention review, production notifications, distributed workers/failover, observability, object storage/scanning, retention operations, identity-backed export signing, measured production load, and formal accessibility/cross-browser certification remain integration gates.
